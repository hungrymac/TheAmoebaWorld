# Amoeba SaaS — エンジニアリング方針

本ドキュメントは、マルチテナント SaaS を長期運用するうえでの**開発の優先順位と境界**を揃えるためのものです。疑義があれば本文とコードレビューで解決し、ここにない慣習を増やす場合は PR で追記を提案してください。

---

## 1. セキュリティとマルチテナント（最優先）

- **他テナントのデータ漏えいは許容しない。** DB では RLS を前提にし、`public` に露出するテーブルは必ず RLS を有効化する。
- **認可に `user_metadata` を使わない。** ユーザーが書き換え可能なため。テナントやロールは **`app_metadata`（サーバー側のみ更新）** または DB の所属テーブルで判定する。
- **サービスロールキーはサーバーのみ。** ブラウザ・`NEXT_PUBLIC_*`・クライアントバンドルに含めない。
- **ビューは RLS をバイパスしうる**ため、Postgres 15+ では `security_invoker` 等の扱いをドキュメント／マイグレーションと揃える。

---

## 2. コードサイズと責務の分割

### 2.1 1 ファイルの行数（目安）

- **推奨上限: 約 500 行**（空行・コメント除く、ESLint の `max-lines` と同じ基準）。
- 超える場合は **分割を検討**する（モジュール抽出、フック分割、サブコンポーネント化、クエリ層の分離など）。
- **例外的に超える場合**は PR 説明に理由（生成物・単一アルゴリズムの塊・移行中の一時ファイルなど）を書く。

### 2.2 肥大化の避け方

- **タスクに直接必要な変更だけ**をコミットに含める。無関係なリネーム・整形の横断変更は別 PR にする。
- **重複ロジック**は `@amoeba/db` / `@amoeba/ui` または小さな共有モジュールに寄せる。コピペの横展開はレビューで止める。
- **SQL の変更**は `supabase/migrations`（または合意したパス）に履歴として残し、本番とローカルの差分が追えるようにする。

---

## 3. 言語・スタイル・Lint

- **TypeScript は strict を維持**する。`any` の常用は避け、やむを得ない箇所は理由と範囲を最小化する。
- **フォーマットは Prettier に一本化**する。口論の時間を減らすため、スタイルの細部は設定に従う。
- **Lint は CI とローカルで同じコマンド**（`pnpm lint`）を通す。
- **Next.js アプリ**は `next/core-web-vitals` + TypeScript ルールをベースにする。
- **`packages/db` / `packages/ui`** は TypeScript ESLint + 行数警告。UI は React Hooks ルールを適用する。

インポートはファイル先頭にまとめる（インライン `import()` の常用は避ける）。

---

## 4. テスト

### 4.1 方針

- **共有パッケージ（`packages/db`, `packages/ui`）**は **Vitest** で単体テストを追加する。ロジック・正規化・権限まわりの純関数を優先する。
- **アプリ（`apps/*`）**は段階的に導入する:
  - 短期: 重要な Server Action / ルートハンドラは **Vitest で分離テスト**可能なら関数化してカバーする。
  - 中期: **Playwright 等の E2E**で「ログイン → ダッシュボード」などクリティカルパスを 1 本以上維持する（別途 `pnpm` スクリプトと CI ジョブを追加してよい）。

### 4.2 最低限の期待

- **新規の純粋ロジック**（料金計算、テナント ID 検証、フォーマッタなど）には **テストを添える**。
- **バグ修正**には可能なら **回帰テスト**を 1 件以上添える。

---

## 5. モノレポと依存関係

- **パッケージマネージャは pnpm**（`packageManager` フィールドに合わせる）。
- **Next が `transpilePackages` で取り込む workspace パッケージ**は、そのバンドルから `import` される **実行時依存**は利用側アプリの `dependencies` にも明示する（解決失敗を防ぐ）。
- **バージョンの乱立**を避けるため、共通の型・Lint 用 devDependency はルートに寄せてもよいが、**実行に必要なものは該当パッケージに宣言**する。

---

## 6. レビューと PR

- **PR は小さく、意図が一つ**に寄せる。巨大 PR は分割する。
- **説明に含めるもの**: 目的、動作確認手順、スキーマ／RLS 変更の有無、破壊的変更の有無。
- **セキュリティ・RLS・認可に触れる PR**はセルフチェックリスト（本書 §1）を踏まえた記述をする。
